# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

There is no Makefile; use plain Go tooling.

```bash
# Build
go build -o /app/main ./main.go

# Run all tests
go test ./...

# Run tests for one package
go test ./internal/config/...

# Run a single test by name
go test ./internal/repository/ -run TestVideoRepository_SomeCase -v

# Vet
go vet ./...

# Local run (requires env vars — see the four 環境設定 tables in README.md)
go run ./main.go
```

There is no local-only mode: `internal/adapters.VertexVeoRunner` talks to real Vertex AI Veo, so exercising the Veo path requires valid GCP credentials, `GCP_PROJECT_ID`/`GCP_LOCATION_ID`, and `AP_MV_BUCKET` (the GCS output bucket). `server.Run` calls `ValidateEssentialConfig()` at startup and will fail fast if required env vars (OAuth, Cloud Tasks, GCS/Veo config) are missing.

Docker build is `FROM scratch` (see `Dockerfile`); `.dockerignore` must exclude `.gocache/` (local Go build cache, can exceed 1GB) or builds become extremely slow.

## Architecture

AP MV is a Cloud Run + Cloud Tasks async orchestrator that turns a "Music Recipe" (song structure JSON) into a synced music video by driving Google's Veo (Vertex AI) video generation and Gemini-based script/keyframe generation. Actual generation logic (Script/Keyframe/Video/Publish workflows) lives in the external module `github.com/shouni/go-veo-orchestrator`; this repo is the web front door, task orchestration, and adapter layer around it.

### Request flow

1. Browser submits a form to `POST /jobs` from `/compose` (the compose page; `command=mv_from_keyframe_video_recipe` has no form page and survives for M2M callers only — see `postVideoRecipeTask`). The handler builds a `Task` and enqueues it via Cloud Tasks (`gcp-kit/worker`), returning a queued page with a `job_id`; that page polls `GET /jobs/{jobID}` (JSON job status) until the job reaches succeeded/failed.
2. Cloud Tasks calls back `POST /tasks/generate` with OIDC verification, which invokes `internal/pipeline` to run the task through the step chain.
3. The step sequence for each task `command` is decided in exactly one place: `DefaultPlanner.Plan` in `internal/pipeline/planner.go` (unknown commands are rejected, both there and in `domain.Task.Validate`). `pipeline.Runner` just resolves workflows (via `WorkflowResolver`, implemented by `builder.workflowResolver`), obtains the plan, and executes it; `pipeline.New(Dependencies)` validates required dependencies at construction. Steps live in `internal/pipeline/step/` (`recipe_load.go`, `scripting.go`, `scene_split.go`, `cut_gen.go`, `zip_upload.go`, `video_gen.go` + `video_gen_chain.go`/`video_gen_prompt.go`, `chain_finalize.go` (concatenates chains, then probes the result via `VideoProcessor.Probe` and warns on a duration mismatch or a missing audio track — the video is still published), `publishing.go`, `regen_cut_keyframe.go`, `section_select.go`, `recipe_save.go` (`RecipeSaveStep`), `cut_video_select.go` (`CutVideoSelectStep`), plus the non-step helpers `recipe_converter.go` and `veo_usage.go`) — file names carry no execution order; check the planner. Each step calls into `go-veo-orchestrator/workflow` runners (Script/CutKeyframe/Video/Publish) and converts between `domain.MusicRecipe` (alias of `genai-kit/music.Recipe`) and `go-veo-orchestrator/ports.VideoRecipe` via `recipe_converter.go`. Commands: `video_recipe_draft` stops one step earlier than anything else — `ScriptingStep` + `SceneSplitStep` + `RecipeSaveStep`, writing the planned `VideoRecipe` to the job's normal `video_music_meta.json` without generating a single keyframe image, so the cut plan can be reviewed before paying for one image per cut. It is not a separate namespace: the job appears in the history list at `script` stage (`domain.JobProgress`), and the detail page's per-cut/per-section regeneration works on it; `video_recipe_create` stops after keyframes + zip; `mv_from_keyframe_video_recipe` runs the full chain from an existing recipe; `short_video_from_section` generates one section only, as an independent short in a new job (`SectionSelectStep` replaces the recipe's cut list with that section's, caps it at 60s, and resets generation state); `section_video` also targets one section but builds up the *same* MV — it generates only the section's **missing** keyframes (`SectionKeyframeStep`), generates only that section's videos (`VideoGenerationStep.SectionScoped`), and writes the **whole** recipe back to the original job (`OriginalJobOutputStep` repoints `fc.OutputPath`). It must never trim the recipe: `enqueueContinuation` carries the recipe in the task payload rather than in storage, so a trimmed recipe would be published over the original job and drop the other sections' cuts. It also omits `ChainFinalizeStep` — combining after every section would leave `final_video_url` indistinguishable from a finished MV — and `finalize_video` performs that combine on demand, generating nothing. Since the continuation overwrites `Command`, `Task.OriginCommand` is what lets the planner restore the section plan. `regenerate_cut_video` redoes one cut's video: `CutVideoSelectStep` keeps every cut in the recipe (chain finalize concatenates all of them, so trimming would yield a short instead of a repaired MV) and resets only the target cut's generation state, leaving the rest `status=generated` for `VideoTimelineRunner` to skip. Its planner chain deliberately omits `SceneSplitStep` — re-planning a recipe whose other cuts already have videos would desync the plan from those artifacts. Under `VEO_USE_PREVIOUS_VIDEO` the reset extends to the end of the target's chain (up to the next chain base), because later cuts in a chain were generated against the target's video as `PreviousVideoURI`; `orchestrator.ChainTailEnd` finds that boundary the same way `runDirect` does (a chain base keeps its planned {4,6,8}s length, extensions are normalized to 7s). Results land in a new job, leaving the original intact. `regenerate_cut_keyframe`/`regenerate_section_keyframes`/`regenerate_zip` are maintenance commands (the two keyframe ones share a step chain — `RegenerateCutKeyframeStep` resolves the target from `cut_index` vs `section_index`, batching a whole section into one `RunAndSave` so its cuts are regenerated together); `video_gen_continuation` is enqueued internally by `VideoGenerationStep` to resume cut-by-cut video generation within Cloud Tasks time limits (generation is resumable per cut, not batch). Note the HTTP path names don't match the command values: the `/compose` route enqueues `video_recipe_create`, `POST /jobs`（`command=video_recipe_draft`） enqueues `video_recipe_draft`, and `POST /jobs`（`command=mv_from_keyframe_video_recipe`） enqueues `mv_from_keyframe_video_recipe`.

`PUT /jobs/{jobID}/recipe` overwrites a job's recipe (ap-mcp's `update_video_recipe`), which is what makes review a *loop* rather than a one-shot read: an agent reads the recipe, rewrites `visual_anchor`/`audio_cue`, saves, and re-reads, all without generating a single image. It is rejected with 409 once keyframes exist: replacing the cut plan after images are baked would leave `keyframe_reference` pointing at the wrong cut. Note that editing cut durations is close to pointless — `SceneSplitStep` re-allocates them from the song timeline at generation time; the fields worth editing are the prompt-side ones. Keyframe *images* are deliberately not producible from outside the pipeline: `go-veo-orchestrator/internal/keyframe/generator.go` builds every keyframe from the character's seed plus its aspect-ratio reference art, and an externally supplied image bypasses both, which is exactly how character identity drifts across cuts.

Script-only jobs used to be "drafts": a separate prefix, filename, listing, job-ID prefix and repository port. They are now ordinary jobs at `script` stage, so one listing, one detail page and one delete path cover them. `/jobs?stage=script` is the old draft list. `GET /jobs/{jobID}/recipe` returns the raw recipe for editing (ap-mcp's `get_video_recipe`), separate from the display-shaped detail response.
4. Results (including `keyframe_reference`, `video_id`, `status` per cut) are persisted as `video_music_meta.json` in GCS under `gs://<AP_MV_BUCKET>/<VEO_OUTPUT_PREFIX>/jobs/<jobID>/`, viewable via `/jobs` and `/jobs/{jobID}`.

### Consistency control in video generation

Veo's biggest failure mode is characters/context breaking across cuts. Several mechanisms keep cuts coherent, and touching `video_gen.go` or `VertexVeoRunner` requires understanding all of them (the five below plus two more that live in `video_gen_chain.go`: `applyChainResetKeyframe` carries the previous chain's last frame into a technical chain reset, and `colorCorrectExtensionCut` counteracts saturation drift on extension cuts):

- **Seed-based determinism** — a per-character seed is reused across cuts.
- **Keyframe anchor (image-to-video / reference-to-video)** — a keyframe image generated from character seed + reference image anchors each cut. When the cut's character has reference art, [character art, keyframe] are sent as Veo's `referenceImages` (asset type, max 3); otherwise the keyframe is sent as the `image` input (image-to-video). `referenceImages` is only supported by non-Fast Veo 3 models (the adapter falls back to `image` otherwise), and Veo rejects `video` + `referenceImages`/`image` together, so when `VEO_USE_PREVIOUS_VIDEO` provides video-to-video context the image references are omitted for that cut.
- **Last-frame interpolation (frames-to-video)** — when a cut resolves to the `image` input path and the model supports `lastFrame` (Veo 2 / Veo 3.1 incl. Fast; not Veo 3.0), the next cut's keyframe is sent as this cut's `lastFrame` so the cut ends exactly on the next cut's opening composition. Guards in the library's `orchestrator.Cuts.NextLastFrameReference` skip it across section boundaries, across different characters, and for duration-split cuts sharing one keyframe.
- **Audio-driven prompting** — each cut's `audio_cue` (e.g. "synchronized with the heavy bass drop at 0:10") is injected into the Veo prompt.
- **Context chain (video-to-video)** — the previous cut's `VideoID` (a `gs://` URI) is passed as `PreviousVideoURI` to the next cut's request, chaining context.

Which Veo feature a request resolves to (`video` / `referenceImages` / `image`+`lastFrame` / `image`) is decided in exactly one place — and that place is **in the library**, `go-veo-orchestrator/ports/veo_mode.go`. `internal/ports/veo_mode.go` holds only type aliases and one-line delegations so ap-mv call sites can keep saying `ports.ClassifyVeoRequest`; it must never grow a second implementation. The model→capability mapping (`ports.VeoModelCapabilities`) and the whole **cut-duration planner** (`ExpandCutsToSupportedDurations` / `SplitCutBySupportedDurations` / `CapCutsTotalDuration` / `ChainTailEnd` / `AllowedCutDurations` / `CutUsesReferenceImages`, plus the duration tables) also live in the library ports — ap-mv used to keep a 325-line copy in `veo_cut_utils.go`, whose helpers had drifted from the library versions; that file is gone and steps call `orchestrator.*` directly. The reason it matters is that the library validates every request's duration against *its* tables before sending (`runner/video.go`, `ErrUnsupportedCutDuration`), so a plan produced by different rules rejects every cut. When adding a new Veo input mode or duration rule, change the library and let ap-mv follow. Chained context travels as `PreviousVideoURI` and **must be a `gs://` URI** — `VideoResponse.VideoID` carries that contract, and the adapter deliberately leaves it empty when Veo returns no URI (an operation name is not chainable context).

Under `VEO_USE_PREVIOUS_VIDEO`, every cut after a chain base is normalized to `veo.VideoExtensionDurationSec` (7s, the only length video_extension accepts) and **a chain is cut off before its cumulative length reaches `veo.ContinuationMaxDurationSec` (24s)** — both constants live in `go-veo-orchestrator/veo`, not here. The reason for 24 is that Veo's real limit on the "previous video" it accepts as extension input is about 30 seconds of accumulated footage, beyond which the request fails with `code=3`, so the planner stops with margin. The cut that starts the new chain is generated without `PreviousVideoURI` (image_to_video or reference_to_video again), and `applyChainResetKeyframe` (`video_gen_chain.go`) swaps its reference image for the previous chain's actual last frame (`VideoProcessor.ExtractLastFrame`, saved as `images/chain_frame_cut_NN.png`) — a fresh generation from the static character art visibly changes costume and framing at every reset, and the last frame does not. `IsSectionStart` cuts are exempt: those are deliberate scene changes (a real song section boundary, or a scene reset that `scene_split.go` planned) and should start from their own keyframe. `colorCorrectExtensionCut` runs after every extension cut: video_extension re-uses the previous output as conditioning, so saturation drifts and **compounds** — measured in production as +20% saturation on the first extension and monotonically rising contrast on each round after. The corrected file (`videos/cut_NN_color_corrected.mp4`) becomes the cut's `VideoURL` *and* `VideoID`, so the next cut chains from the corrected video and the drift does not accumulate. The correction target is the cut's own `KeyframeReference`, **never `char.ReferenceURL`**: the character sheet is a three-view turnaround on white, whose background pulls the mean saturation down to ~5.2 (`SATAVG`) against ~28.6 for a real scene keyframe, and matching to it produced washed-out video in practice. Both steps are skipped when `VideoProcessor` is nil (tests, or the workflow path).

`SceneSplitStep` must stay idempotent: both `mv_from_keyframe_video_recipe` (RecipeLoad → SceneSplit over a stored recipe) and the draft flow re-run it over an already-split recipe, and a second pass that re-plans would silently change the cut plan the user just reviewed. The subtle part is `IsSectionStart`: on a fresh recipe it is set from the sub-block index (`i > 0`), but a re-split turns every already-allocated block into a single block (`i == 0`), so the scene resets would be lost — `expandCutsForVideoToVideoScenes` carries them over by reading `IsChainStart && IsSectionStart` *before* `resetCutForSceneKeyframe` clears both. `TestSceneSplitStepIsIdempotent` pins this; `RecipeSaveStep` relies on the same property to hand a draft to `mv_from_keyframe_video_recipe` unchanged.

Cut durations treat the song timeline as the source of truth: Veo only accepts discrete durations ({4,6,8}s bases, 7s extensions), so `SceneSplitStep` allocates each cut's length from the achievable chain lengths (`videoToVideoChainDurations`, derived from the base durations and the 24s continuation cap — do not hardcode the set; as of go-veo-orchestrator v1.15.0 it comes out as {4,6,8,11,13,15,18,20,22} for an image_to_video base and {8,15,22} for a reference_to_video base) with per-cut rounding error carried into the next cut's target (error diffusion), then re-bases `StartSec`/`EndSec` onto the concatenated-video timeline so cuts never overlap. Planned chain blocks are marked `IsChainStart` and `expandCutsToSupportedDurations` realizes them as `[base, 7s, ...]` without rewriting their durations; cuts without that flag (old recipes, `SectionSelectStep`) fall back to greedy 8s splitting + cumulative chain formation.

Keyframe images are reused rather than re-baked when a job runs again over an already-planned recipe (e.g. history detail's "generate video → full MV", which goes through `RecipeLoad → SceneSplit → CutKeyframe`). The decision itself lives in the library: `CutKeyframeRunner.RunAndSave` generates only the cuts whose `KeyframeReference` is empty. ap-mv's job is to make sure the surviving references are correct and reach it — two steps do that. `SceneSplitStep` keeps a cut's `KeyframeReference` when the cut re-allocates to exactly one block (a re-split cut drops it, since one image can't stand for several cuts that each get their own scene beat), and `RecipeLoadStep` absolutises job-relative references against the job the recipe came from — a relative path would otherwise satisfy the library's non-empty check while pointing at nothing under the new job's output path. To deliberately re-bake, use `regenerate_cut_keyframe` / `regenerate_section_keyframes`; picking up changed character art or seeds requires one of those, not a video re-run.

Resumability depends on per-cut `status`/`video_id`/`video_url` in `video_music_meta.json`: cuts already `status=generated` are skipped by `VideoTimelineRunner` and their `video_id` is reused as the next cut's `PreviousVideoURI`, so re-submitting a recipe resumes rather than restarts.

### Continuation tasks and the re-run guard

- **`handlers.enqueue` records `queued` before it enqueues, and deletes the record if the enqueue fails.** Cloud Tasks delivers within tens of milliseconds, so recording after the enqueue lets a late `queued` overwrite the worker's `running` and the job then reads as never started; ap-story and ap-voice both hit that order in production, and the worker convention in public-docs (§2.1) fixes it. `TestEnqueueRecordsQueuedBeforeEnqueue` pins the order and the rollback.
- **`VideoGenerationStep.runDirect` generates one cut per task.** After each cut, if pending cuts remain in scope, `enqueueContinuation` puts the in-progress recipe into a `video_gen_continuation` task (same `job_id`, `origin_command` = the command being continued, `video_recipe` carried **in the payload**, not re-read from storage) and returns `step.ErrPipelineDeferred`. `Runner.run` turns that into a `deferred` result and `recordOutcome` **leaves the record at `running` and sends no notification** — marking it `succeeded` would arm the re-run guard against the very continuation that carries the same `job_id`. The point is Cloud Tasks' per-request time limit: a long MV cannot fit one dispatch, and `PIPELINE_TIMEOUT` applies to each continuation separately.
- **The continuation is enqueued under a deterministic name** (`continuationTaskID` = `<jobID>-cont-cut-<n>`, via `TaskQueue.EnqueueWithName`), so an at-least-once redelivery that reaches the same completed cut has its second enqueue rejected as a duplicate instead of fanning out into two chains. It does not stop the redelivered execution from regenerating that cut — that would need authoritative per-cut state read before every generation.
- **If the enqueue fails, the job stops there.** The queue runs with `max_attempts = 1`, so nothing redelivers; the generated cuts are already persisted, so re-submitting the recipe resumes. This is deliberate while the pipeline is still being validated: retries would hide systematic bugs behind transient recoveries, and every regenerated cut doubles the Veo bill. Raising `max_attempts` later makes the resume automatic without code changes.
- **The re-run guard is per job, not per cut.** `statusRecorder.begin` (`gcp-kit/jobstatus.Recorder.Begin`) reads the record once, returns early when it already says `succeeded`, and otherwise writes `running` and bumps `Attempts` in the same read-modify-write — so no other delivery can slip in between. Without it, a worker that errored only on the notification would be redelivered and pay for the whole generation again. An unreadable record returns an error and records nothing: defaulting to "not done" re-runs a finished job, defaulting to "done" ACKs an unfinished one forever. A redelivery that lands while the job is `running` is *not* caught, so duplicate generation of one cut is still possible there.
- **Failure is recorded on the detached context.** `worker.Lifecycle` calls `Finish` (record + notify) on a context it detached from the request, so a `PIPELINE_TIMEOUT` or a Cloud Tasks cancellation still produces the `failed` record and the Slack message. Success and failure go through the same `recordOutcome`, so a forgotten detach cannot happen on one side only.
- **`veo_usage.json` is the ledger of what was actually billed.** `recordVeoUsage` runs right after every successful `runner.Run` — the moment billing happens — and read-modify-writes `{outputPath}veo_usage.json` with count, seconds and model per cut. `video_music_meta.json` can only yield the *finished* footage; cuts regenerated by a redelivery or by `regenerate_cut_video` never show there, and the difference is what the history detail displays as regeneration waste. A failed write only warns and generation continues, because stopping for bookkeeping would make Cloud Tasks re-burn an already-billed cut. Two jobs writing the same file concurrently can lose an update, so the ledger may under-count.

### Auth model

Two independent auth paths guard `/*`:
- Browser sessions: Google OAuth via `gcp-kit/auth/session`, with the session itself stored in Firestore (`SESSION_FIRESTORE_DATABASE` / `SESSION_FIRESTORE_COLLECTION`, a **different database from the job-status one** — a database name is an identifier that cannot be renamed later, so sharing leaves one of the two misnamed). The cookie carries an opaque ID and nothing is signed client-side, so there are no session keys to rotate. CSRF tokens (form field `csrf_token`, or `X-CSRF-Token` header for JS `fetch` calls like DELETE) are stored server-side in that session and compared in constant time, which is what keeps validation stable across restarts and multiple Cloud Run instances.
- Machine-to-machine: OIDC Bearer tokens (`Authorization: Bearer <ID Token>`, audience = `SERVICE_URL`) from service accounts listed in `ALLOWED_M2M_SERVICE_ACCOUNTS`. Requests authenticated this way bypass CSRF checks and can request JSON responses via `Accept: application/json` (used by ap-mcp and other service-to-service callers). **`ALLOWED_M2M_SERVICE_ACCOUNTS` is required on the web face and `newM2MVerifier` fails startup without it** (unlike ap-voice, where it is optional): `auth.Protected` cannot switch M2M off, and a web service started without the list looks healthy in a browser while ap-mcp alone receives the login page's HTML — a failure nobody notices until an agent call breaks.

### History screens and media URLs

- **Signed URLs are never embedded in HTML.** The page links to same-origin paths (`/jobs/{jobID}/metadata`, `/video`, `/cuts/{n}/video`, `/cuts/{n}/keyframe`) and the handler answers each with a 302 to a freshly signed URL (`job_media.go`; the 302 itself is cached `private, max-age=600`, shorter than the signature). Embedding had two problems: a signed URL works outside the app's authentication for as long as it is valid, and the detail page is where cuts are compared before deciding to regenerate, so it stays open long enough for the signatures to expire — playback then 403s until a manual reload. The redirect also removes the dozens of IAM SignBlob round trips a single detail render used to pay up front (Cloud Run holds no private key, so signing is a network call, not local math). **Only the JSON representation carries signed URLs** (`SignHistoryURLs` in `serveDetail`), because ap-mcp consumes the URL itself rather than following redirects.
- **The list is a Firestore query; the detail and the keyframe zip read GCS.** `GET /jobs/{jobID}` reads the status record once and, for a finished job, `video_music_meta.json`; `DownloadKeyframes` streams `cut_NN.png` plus `inputs.txt` (ffmpeg concat demuxer, keyframed cuts only) and `subtitles.ass` (cuts with dialogue) straight from storage. The list orders by `queued_at` descending; the *displayed* creation time is the UTC mint time embedded in the job ID (`go-utils/jobid.CreatedAt`, also valid for ap-music's `music_job_id`), converted with `go-utils/jst`, so it does not depend on the runtime's timezone. The two composite indexes the list needs are `mv_history` and `mv_history_stage` in ap-infra; a query without its index fails at runtime and the emulator does not catch it.
- **Deleting a job deletes its status document explicitly** (`handlers.deleteJobStatus`). The record lives in Firestore, outside the job's GCS prefix, so the prefix delete does not take it with it; without this call the record of an artifact-less job would sit in the list forever. A failed status delete only warns, since the artifacts are already gone. The list offers Delete on jobs with no artifacts for the same reason: their detail page cannot render (there is no `video_music_meta.json`), so the row is the only place they can be removed from.

### Environment variables

The full list of runtime env vars with defaults is in README.md's 環境設定 section, split into four tables by role (every role / web / worker / optional) — check there before adding or changing config rather than re-deriving it from `internal/config/config.go`. Listed below are only the ones carrying a rule that is easy to break by editing.

- **The worker enqueues too, so the Cloud Tasks set is required for every role.** Unlike ap-music, `CLOUD_TASKS_QUEUE_ID`, `WORKER_URL` and `TASK_CALLER_SERVICE_ACCOUNT_EMAIL` are validated regardless of `SERVER_ROLE`, because `VideoGenerationStep` re-enqueues its own continuation cuts. `WORKER_URL` is derived from `SERVICE_URL` only on a role that serves the worker face (`normalizeWorkerURL`): on a split deployment `SERVICE_URL` is the public URL, so deriving it on `web` would send every task to a 404. The worker's `ALLOWED_TASK_SERVICE_ACCOUNTS` therefore lists **both** the web SA and the worker SA. `SERVICE_URL` on the worker is still the *web* URL — the Slack link to the history detail is built from it.
- **`TASK_AUDIENCE_URL` must be the worker's own URL on a split deployment.** It falls back to `SERVICE_URL`, which is fine for `both` and wrong once the faces are separate: Cloud Run's IAM rejects an audience mismatch with 403 before the container sees the request.
- **`PIPELINE_TIMEOUT < TASK_DISPATCH_DEADLINE <= Cloud Run timeout`, enforced at worker startup** (`validatePipelineTimeout`; equality and unlimited are both rejected). The smallest of the three wins. The app must give up first: when Cloud Tasks cuts the request, the process is stopped mid-job, the failure record and the Slack notification never run, and with `max_attempts = 1` on the queue nothing retries — the job stays `running` forever. The record is written on the detached `Finish` context precisely so that the app's own timeout *can* report itself. Neither value has a default: the ladder is decided by the deployment, and an app-side default would duplicate the number in two places and let a missing setting run on a value nobody chose. Note Cloud Tasks' own default dispatch deadline is **10 minutes**, so forgetting `TASK_DISPATCH_DEADLINE` truncates the worker at 10 minutes no matter how long the Cloud Run timeout is. The fleet-wide ladder and the Terraform `precondition` checks are in ap-infra's README.
- **Why web and worker are separate services** (one image, `cloudbuild.yaml` deploys both): the worker needs a timeout of tens of minutes that the web face should not inherit; Cloud Run metrics are per service, so a co-located long job dominates p99 latency and hides the web face's own memory peak; and `/tasks/generate` on a public service is guarded only by the OIDC middleware, whereas a separate service with `internal` ingress is rejected by IAM before the container is reached. `SERVER_ROLE=both` exists for local screens only — Cloud Tasks cannot deliver to localhost, so the pipeline never runs there.
- **`SERVICE_URL` and `WORKER_URL` must be HTTPS** — `netarmor/securenet.IsSecureServiceURL` in `ValidateEssentialConfig`. Outbound HTTP goes through `go-http-kit`'s guarded client and GCS through `go-remote-io`; nothing here fetches with a bare `http.Client`.
- **`KEYFRAME_MAX_CONCURRENCY` / `KEYFRAME_RATE_INTERVAL` feed one limiter in go-veo-orchestrator** that spaces *every* AI call — keyframe images and the script text generation alike, because the quota is per project, not per model. Throughput therefore caps at `1/KEYFRAME_RATE_INTERVAL` regardless of concurrency; raising both is a contradiction that `warnContradictoryKeyframeThroughput` logs at startup with the effective images-per-minute, since the misconfiguration otherwise looks like it is working. The same library package also de-duplicates identical in-flight requests (`workflow/singleflight.go`).

**Model names have no defaults anywhere in this repo.** `GEMINI_MODELS` / `IMAGE_MODELS` / `VEO_MODELS` are required for every role and `ValidateEssentialConfig` fails startup when one is empty. The singular `AIConfig.GeminiModel` / `ImageModel` / `VeoModel` are `env:"-"` and derived from the head of each list (same shape as ap-music) — there is no `GEMINI_MODEL` / `IMAGE_MODEL` / `VEO_MODEL` env var. `NormalizeModelList` and `NormalizeDefaultModel` return empty rather than substituting a fallback, and `handlers.ModelOptions.normalize` does not fill one in either — that would make a missing setting look fine in the form. Model IDs age on Google's release schedule, not this repo's, so the value belongs in the deployment config (`ap-infra`). There used to be a `domain/model_defaults.go` whose constants had to be kept identical to the `envDefault` struct tags by hand; it is gone, and so is that class of drift. `VEO_PRICE_USD_PER_SEC` has no default table either — model names and prices both change on Google's schedule. An unset table prices every model at `domain.DefaultVeoPriceUSDPerSecond`, so the history cost column degrades to a flat estimate rather than breaking.

## VideoRecipe validation

`domain.ValidateVideoRecipe` delegates to `orchestrator.VideoRecipe.Validate` — the rule lives with the type, in `go-veo-orchestrator/ports`. Two entry points share it:

- `VideoScriptRunner.Run` validates every AI-generated script and regenerates up to `maxScriptAttempts` times. JSON Schema constrains types and required fields only, so an empty `cuts` list or a `section_index` past the music recipe's sections slips through and would otherwise surface during Veo cut generation — the most expensive step.
- `domain.UnmarshalRecipeOrVideoRecipe` validates hand-supplied recipe JSON on the way in.

Do not re-implement the checks in ap-mv: adding one here and not there is how the two paths drifted apart before (only the hand-supplied path was validated).
